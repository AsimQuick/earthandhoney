# AC-34.6 — Homepage performance, measured against PRD 19.4

## What was measured

The real homepage (`/`), served by the same production build/start container
(`web-benchmark`, `docker-compose.yml`'s `benchmark` profile) US-29's own
ADR measurements use — never the dev-mode `web` service, which
`scripts/benchmark/run.ts`'s header already documents as producing
artificially bad, non-reproducible numbers. Lighthouse ran with its default
mobile form factor and mobile-representative simulated throttle (see
`scripts/benchmark/ac34.2-hero-cls-measurement.ts`, reused unmodified —
that script already targets `/` with the same `collectRun` Lighthouse
invocation `run.ts` uses for the two US-29 benchmark pages).

The hero slideshow placement (AC-34.3) was pointed at a real, seeded
Backstage gallery — `scripts/ac34.6-homepage-hero-benchmark-seed.sh` — so
the homepage's `<img>` requests actually hit
`/api/gallery/:slug/hero/:photoId`, the `backstage-proxy` delivery
mechanism (candidate 1 in `R2_STORAGE_AND_DELIVERY_ADR.md`), rather than
falling back to `GalleryUnavailablePlaceholder`'s placeholder markup, which
carries no photograph for LCP to measure. `StudioProfile.homeHeroGallerySlug`
was `null` before and after this measurement (restored via the same
`/api/globals/studio-profile` route the seed script used to set it) — this
repository's shared `db` Postgres volume is left exactly as it was found.

Raw evidence retained in this directory: `ac34.2-hero-cls-2026-08-14T10-22-39-394Z.json`
(3 Lighthouse passes, `runsPerPage: 3` — a single run is not a measurement,
mirroring AC-29.1.2's own floor).

## Measured figures vs the PRD 19.4 targets

| PRD 19.4 target | Measured (median, 3 passes) | Spread (min–max) | Verdict |
|---|---|---|---|
| No image-caused cumulative layout shift | CLS(image-attributable) = **0.0000** | 0.0000–0.0000 | **PASS** |
| Mobile-first Lighthouse performance near or above 90 | **0.91** (91/100) | 0.85–0.91 | **PASS** — median clears the target; one pass of three (0.85) would not have |
| LCP approximately 2.5 seconds or better, realistic mobile profile | **3410ms** | 3408ms–3472ms | **FAIL** — every one of the 3 passes missed, not just the median |

Public pages never requesting full-resolution originals unnecessarily: 0
images flagged oversized by Lighthouse's `image-size-responsive` audit
across all 3 passes — consistent with the other three targets, cited here
for completeness though it is not this AC's headline figure.

The remaining PRD 19.4 targets (fullscreen-viewer perceived-instant open,
contact-sheet pagination/virtualization at scale, resumable batch upload
retry) describe interactions this static homepage measurement does not
exercise and are out of this AC's scope.

## The LCP gap

Measured median LCP is **3410ms** against a target of **~2500ms or
better** — a gap of **≈910ms (36% over target)**. This is not run-to-run
noise: `scripts/benchmark/results/REPRODUCIBILITY.md` (US-29) recorded up
to ~78ms of spread between back-to-back invocations of this same harness on
comparable pages: at 910ms over target, this run's gap is roughly twelve
times that noise floor, on every one of the 3 passes (3408ms, 3410ms,
3472ms), not just the reported median.

## Is the open R2 delivery-path decision a contributing factor? Yes.

The homepage hero is served today through **candidate 1 — the Backstage
token-gated proxy (`backstage-proxy`)** — the same mechanism
`R2_STORAGE_AND_DELIVERY_ADR.md`'s own AC-29.3 measurements already cover.
That ADR recorded candidate 1 **failing** the identical ~2.5s LCP target on
both its representative pages (portfolio-gallery: 3585ms/3581ms median
across two invocations; story-gallery: 3214ms/2575ms). This homepage
measurement's 3410ms median LCP sits inside that same range — it
corroborates the ADR's existing candidate-1 finding rather than surfacing a
new, homepage-specific problem.

`R2_STORAGE_AND_DELIVERY_ADR.md`'s delivery-path decision remains
**UNDECIDED** (`scrum-master/po-requests.md` item 15 — candidates 3 and 4
need infrastructure that does not exist yet, and per that ADR's own
standing rule, no agent may choose a path by preference ahead of that
decision). Because the homepage's LCP miss tracks the already-measured
candidate-1 shortfall, image-delivery latency is a known, named,
**unresolved** variable in this result, not a defect specific to the
homepage template built in US-34. **This document does not choose a
delivery path** — that decision belongs to the process
`R2_STORAGE_AND_DELIVERY_ADR.md` and `po-requests.md` item 15 already
govern, not to this AC.

## Reproducing this measurement

```
docker compose --profile backstage up -d
docker compose --profile benchmark up -d --build web-benchmark
scripts/ac34.6-homepage-hero-benchmark-seed.sh
docker compose --profile benchmark run --rm --entrypoint 'npx ts-node --compiler-options "{\"module\":\"commonjs\",\"moduleResolution\":\"node\"}" ac34.2-hero-cls-measurement.ts' lighthouse-benchmark
```

Then restore `StudioProfile.homeHeroGallerySlug` to its prior value via
`POST /api/globals/studio-profile`, as the seed script's own final message
instructs.
