# AC-33.5 live proof — the studio notification goes through the Backstage email queue

## Why this document exists

AC-33.5's evidence clause asks for two things that a unit test cannot give,
because both are properties of a running system rather than of source code:

1. the notification **observed queued and then sent**, confirmed
   *independently in the mail catcher* — "not inferred from a return code";
2. the **client-side bundle and network requests checked** to confirm no SMTP
   secret is ever sent to or present in the browser.

Two committed scripts produce exactly those two transcripts, and both were run
to completion on **2026-08-14** against the stack in Docker. The unit suites
(`src/__tests__/us33-ac33.5-*.test.ts`) cover the request shape, the failure
paths, and the static source invariants; this document covers what only a live
run can show.

## What is being proven, and why it matters

`SYSTEM_OWNERSHIP.md` and CLAUDE.md's System Ownership table name **the
PicPeak/Backstage email queue** as the single authoritative owner of all client
and photographer email. The tempting shortcut — Payload or Next.js opening its
own SMTP connection for one small notification — would create a second sender
identity, a second brand, a second place templates are edited, and a second
system holding an SMTP credential. Resend, the retired option, is excluded
outright (CLAUDE.md, "Retired From the Old Direction"). So the thing to prove
is not "an email arrived", it is **"the email arrived, and Backstage is what
sent it."** That is why the queue row is read out of Postgres in both its
`pending` and `sent` states: the `pending` read is the evidence that Frontstage
handed the work over rather than doing it, and the MailHog read is the evidence
that the handover actually completed.

## Proof 1 — queued, then sent, then seen in the mail catcher

**Script:** `scripts/ac33.5-email-queue-live-proof.sh` (with
`scripts/ac33.5-email-queue-live-proof.ts`, the in-container half).
**Prerequisite:** `docker compose --profile backstage up -d`, per
`BACKSTAGE_STARTUP.md`.

The script deliberately does **not** `curl` the new route. A `curl` would only
prove the fork's route works; it would say nothing about the code this AC
actually delivers. Instead it runs the real, unmocked
`src/lib/inquiryNotification.ts` inside the `web` container, against the live
`backstage-backend` over the Docker network — so the thing under test is the
Frontstage module itself.

It also empties MailHog before the run and tags the submission with a unique
marker, so nothing found afterwards can be a leftover from an earlier session.
A run that cannot find its own marker in MailHog **fails**; a queued row that
never actually left Backstage can therefore never pass.

### What each leg establishes

| Leg | Establishes |
|---|---|
| 1 | The credential is a **scoped Bearer API token minted through the fork's own admin route** — not a hand-written database row and not an admin session cookie. `write` scope, the same pair `v1/events.js` uses. |
| 3 | The **real Frontstage module** made the call. `sendInquiryNotification` resolving means it queued; the module contains no SMTP code and reads no SMTP credential, so it could not have sent anything itself. |
| 4a | The row exists in Backstage's `email_queue` as **`pending`, `event_id` NULL**. This is the crux: at this instant the email demonstrably has *not* been sent, and it is demonstrably *Backstage's* to send. |
| 4b | Backstage's own processor moved it to **`sent`** with a `sent_at` timestamp, `error_message` empty, `retry_count` 0 — through the fork's own transport, from the fork's own `from_email`. |
| 5 | **Independent confirmation.** The message is read out of MailHog's own API, not out of any response body: correct recipient, the template's rendered subject, and the run's unique marker inside the `Label: value` submission summary in both the text and HTML parts. This is the "not inferred from a return code" requirement. |

Note the `From:` address — `noreply@photo-sharing.local`, Backstage's own
configured sender, rendered from the `inquiry_received` template added by
migration `120_add_inquiry_notification_email_template.js`. Frontstage supplied
no sender, no subject, and no HTML; it supplied five data fields and let the
authoritative system render and send. That is the ownership boundary holding in
practice, not just on paper.

## Proof 2 — no SMTP secret reaches the browser (PRD 20.3)

**Script:** `scripts/ac33.5-no-smtp-secret-in-browser-proof.sh`.

The static guard `src/__tests__/us33-ac33.5-no-smtp-secret-in-browser.test.ts`
proves the *source* never references a secret outside one server-only module.
This proof covers the other half — **the artefact the browser actually
receives**, which is what PRD 20.3 is about.

The method: run a real production `next build` with deliberately distinctive
sentinel values loaded into every secret this AC touches
(`BACKSTAGE_API_TOKEN`, `SMTP_PASSWORD`, `SMTP_PASS`, `SMTP_USER`), then grep
every byte the browser can fetch for those sentinels. A production build is
used rather than a dev server on purpose: `next dev` serves unminified,
on-demand modules, so a secret inlined only by the production compiler would be
missed. The sentinels are invented nonsense strings, never real credentials,
which is why this transcript is safe to commit.

Two honest notes about that transcript, so it is not read as claiming more than
it shows:

- The three routes returned identical 12,575-byte bodies. The build container
  has no seeded Payload content, so `/weddings` and `/engagements` served the
  same shell as `/`. That does not weaken the check — the scan covers the whole
  of `.next/static` (94 files, ~3.5 MB, every chunk the client can request,
  reachable page or not), and the per-route leg is an additional network-level
  confirmation on top of it, not the primary evidence.
- Both the sentinel **values** and the secret **names** are searched. The name
  check is the one that keeps working after the values change: if a future
  refactor ever inlines `process.env.BACKSTAGE_API_TOKEN` into a client
  component, the name appears in a chunk and the run fails even though no real
  secret leaked yet.

### Why no SMTP secret can be in the browser at all

The structural reason, which the greps confirm rather than establish:

- **Frontstage holds no SMTP credential of any kind.** It does not send email.
  The SMTP host, port, and sender live in Backstage's own `email_configs` row,
  read by Backstage's own transporter, inside the `backstage-backend` container.
- The single secret Frontstage does hold for this flow, `BACKSTAGE_API_TOKEN`,
  is read in exactly one module, `src/lib/inquiryNotification.ts`, which is
  imported by exactly one file: `src/app/(frontend)/api/inquiries/route.ts`, a
  Next.js Route Handler — a module class the App Router never bundles for the
  client. Neither file carries a `'use client'` directive, and the variable
  carries no `NEXT_PUBLIC_` prefix, which is the only mechanism by which
  Next.js inlines an env var into a client bundle.
- The route handler returns `{ id }` and nothing else. It never echoes a
  Backstage response body, so nothing the email queue returns can reach the
  browser either.

All three points are enforced by the static suite, so a future change that
breaks any of them fails in CI without needing a Docker daemon.

## Reproducing both proofs

```
docker compose --profile backstage up -d          # per BACKSTAGE_STARTUP.md
scripts/ac33.5-email-queue-live-proof.sh          # proof 1
scripts/ac33.5-no-smtp-secret-in-browser-proof.sh # proof 2 (runs a full next build)
```

Each script mints or invents whatever it needs and exits non-zero on failure,
so neither depends on state left behind by the recorded run above. Proof 1
mints a fresh API token per run and tags its submission with a fresh marker;
proof 2 needs no Backstage profile at all, since nothing is sent — only built
and inspected.
